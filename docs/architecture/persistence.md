# Persistence and ephemeral infrastructure

Platform/data owners maintain `@daisy/db`; application features call its public operation API. Drizzle and Bun SQL stay private. Tables are organized by record ownership; do not grow one giant schema file. Domain snapshots are serialized values, not database rows or ECS internals. The adapter stores a JSON snapshot plus searchable identity/resolution/format and the lifecycle projections `mode`, `phase`, `visibility`, `started_at`, `completed_at`, `outcome` (ADR 0029). Consumers validate loaded snapshots with the domain/protocol decoder before use. `createdBy` references `actors`, never `users`, and is nullable for service-originated architectural proofs.

`@daisy/db`'s `createDatabase()` composes one module per area (auth, debates, actors, email, outbox — `*-operations.ts`, plus `outbox.ts`'s own `outboxOperations`), each taking only the opaque Drizzle handle and the event sink, never a raw table or transaction. Every operation reports failure through the package's one `instrumented(eventSink, operation, fn)` wrapper (`instrumented.ts`); the two `session.revoked` outbox appends (`appendSessionRevoked`, `revokeOtherSessions`) share one `appendSessionRevokedFor` (`session-revoked.ts`). `transaction`, `createUser` and `saveSnapshot` have no production consumer (ISSUE-8, review T5) and are therefore not part of `createDatabase()`'s return value; `packages/db`'s own tests reach them through `test-only-operations.ts` or a direct submodule import, never through the public `@daisy/db` export.

Identifiers are application-generated cuid2 values before writes (ADR 0018), shared across protocol/domain/persistence; PostgreSQL stores them as text and never generates them, and exactly one identifier shape is accepted anywhere (ADR 0023 withdrew the UUID carve-out), with one documented exception: `formats.id` is a canonical slug such as `foundation` (ADR 0030). Timestamps use timestamptz and UTC ISO strings, durations use integer milliseconds. `createdAt` is immutable; mutations explicitly update `updatedAt`. Version begins at 1; `saveSnapshot` updates only the expected version and returns null on conflict. A retry re-reads current state and reruns domain rules. Do not blindly replay stale snapshots. Account deletion tombstones the user (ADR 0029): the row keeps its id, `deleted_at` is set and PII is scrubbed (`email`, `username`, `image` NULL, `name = ''`, enforced by CHECK); auth rows are deleted and active role grants revoked in the same transaction, while the user's actor and competitive history stay intact. Username normalization belongs in the future identity application operation.

`createDebate` runs within an explicit transaction. Future compound operations belong in focused adapter functions sharing one transaction, not a generic repository wrapper. Concurrency-sensitive operations must document transaction boundary, duplicate delivery, retry budget, stable command/idempotency key, and conflict behavior. Unique debate IDs already prevent duplicate creation; this is not complete idempotency (a duplicate may have different payload). Full idempotency needs a durable key plus payload digest and result in the same transaction; `debate_commands` is that table, and its writer lands with the first real command consumer.

Revoking all of a user's sessions is serialized against session creation in the database (ISSUE-22, owner decision 2026-09-23): `revokeOtherSessions` first takes the user row `FOR UPDATE`, which conflicts with the `FOR KEY SHARE` lock every `session` insert's `user_id` foreign-key check holds until commit, and only then deletes, in a second statement whose Read Committed snapshot postdates the lock. An insert still uncommitted when the revoke starts is therefore waited for and deleted; one that starts later lands after the revoke. It is the only revoke-all: the email change and both self-service revoke-all endpoints use it, and so must every future one (recovery, admin ban). The email change's final step, `completeEmailChange`, moves the address and deletes the old address's outstanding sign-in links in one transaction (ISSUE-99).

Redis is never authoritative for results, ballots, ratings or recordings metadata. Keys are `<deployment>:v1:<validated-segment>`; expiry is mandatory and set atomically with the value. Isolate deployments through namespace and credentials. Tests get unique namespaces and delete only their own keys. No global flush. Cache/presence loss must be recoverable from authoritative state. Rate limiting requires an atomic server-side operation and explicit outage policy before public mutations ship; in-memory limiters are not multi-instance enforcement.

Authentication mail diagnostics live in `email_delivery`, `email_delivery_event` and `email_suppression` (ADR 0025): message and event IDs, a monotonic status rank and a keyed SHA3-256 recipient hash only — never an address or a provider payload. The web server's one retention sweep (`apps/web/src/server/retention-sweep.ts`) deletes `email_delivery_event` rows 30 days after receipt, `email_delivery` rows 30 days after their last status change and expired `verification` rows after a 24 h grace; `email_suppression` rows are never pruned. Rate-limit counters are Redis-only (`<namespace>:v1:rl:<sha3-256>`, one atomic Lua `EVAL`, always expiring).

## Competitive tables (ADR 0029)

One schema file per ownership area under `packages/db/src/schema/`. Every status column is `text` plus `CHECK`, every id is an app-minted cuid2, every concurrently mutated row carries `version > 0` (`role_grants` is append-then-revoke and has none), and every CHECK vocabulary that has a protocol counterpart (`debateRoles`, `phaseSchema`) is built from it.

## Roles, jsonb and the baseline (ADR 0038)

The single baseline creates the runtime roles. `daisy_web` is the web
application's: DML on every `public` table and use of every sequence, and
by default privileges on every table a later migration adds, but no schema
changes, no `TRUNCATE` and no migration log. `daisy_realtime` gets only ADR
0032's explicit grants. The browser suite's loopback login `daisy_e2e` is a
member of `daisy_web` with no grant of its own, provisioned only by
`provisionTestRoles` (`bun slot:up`, `bun db:reset`, `bun slot:reset-e2e`,
CI's `bun db:roles`).

Every jsonb column is a `jsonbColumn(name, schema)`: each write is parsed
with the column's schema and a mismatch fails with an `AppError`
`VALIDATION` before the driver sees it, and a `<table>_<column>_is_object`
CHECK refuses a scalar or array written around the adapter. Every foreign
key has a full index leading with its columns; every timestamp column is
`timestampColumn` (timestamptz, Date mode).

## Realtime, presence and adjudication (ADR 0033)

Forward-migration intent recorded ahead of the leaves that build it. Nothing
below exists yet. Migration generation is single-writer, so these land one at
a time in this order: `outbox` (RT-2.2, which also creates the realtime
role), `users.presence_visibility` (RT-3.2b), the rules shape (RT-4.1),
`service_instances` and `availability_samples` (RT-4.3a, RT-4.3b), the
`debate_commands` operation key (RT-4.4), `debates.outcome_reason`
(RT-4.5b).

No check-in table exists. A check-in is an attendance entry
`{turnIndex, participantId, receivedAt}` in the debate snapshot, recorded
under the debate row lock. The evaluator records each adjudicated speech
turn as `{turnIndex, decision}` in the snapshot and a `debate_commands` row
under its service principal. Both writes are made unique by the operation
key. Turn boundaries are computed from `debates.started_at` and the
effective rules, never persisted per turn. Every competitive time
(`started_at`, check-in receipts, lease renewals, samples) is PostgreSQL
time. A check-in uses the `statement_timestamp()` of its transaction's
first statement, taken before the row lock.

A new login role, `daisy_realtime`, serves `apps/realtime`. It gets
`SELECT` on the outbox and on the read models it needs: the list for
authorization and revalidation is ADR 0032's, plus the seats and
`users.presence_visibility` for presence doorbells. On `service_instances`
it gets `INSERT` and `UPDATE` only, with no `DELETE` or `TRUNCATE`
anywhere. It writes nothing else. The web role (`daisy_web`, ADR 0038)
reaches the new tables through its default privileges and runs the
stale-row prune.

Presence is Redis-only and advisory. Each connection has a lease,
`<namespace>:v1:presence:conn:<connId>`: a hash with its own 60 s TTL,
refreshed every 20 s. The leases are indexed by three sorted sets:
`<namespace>:v1:presence:actor:<actorId>` and
`<namespace>:v1:presence:online` (RT-3.1), and
`<namespace>:v1:presence:debate:<debateId>:spectators` (RT-3.3). Each set
is scored by lease expiry from Redis `TIME` and carries its own expiry,
set in the same Lua script. Every write is one atomic Lua op, and every
read is one Lua op that trims, ranges and hydrates. Competitive outcomes
never read presence.
