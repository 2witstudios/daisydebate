# 0038: Drizzle 1.0 and the single baseline that owns roles, rules and reference data

Status: accepted (ISSUE-6, ISSUE-17, ISSUE-24; owner decisions of
2026-09-23). Supersedes ADR 0012's "never switch to an RC" sentence for
Drizzle, ADR 0023's journal-fingerprint sanction mechanism, and the
template database and e2e grants of ADR 0034. Amends ADR 0007 and ADR 0029
as noted below. Amended by ADR 0039: the rejection of `bun audit --ignore`
and exception registries below no longer holds for the two dated,
unreachable advisories that ADR 0039 lists.

## Context

Before first ship `packages/db/migrations` held five drizzle-kit 0.31
migrations. `0002` truncated `debates`, `0004`'s comments narrated an e2e
failure, and `meta/0005_snapshot.json` had been orphaned and was invisible
to `bun migrations:check`, which read only the journal. The web app and the
tests connected as the migration owner `daisy`. The browser suite's
`daisy_e2e` login was defined three ways (`slots.ts`, `ci.yml`, and
`e2e.yml`, which made it the superuser), and its grants lived in a template
database and in `0004`, so `bun db:reset` dropped them and the production
server under e2e failed sign-up with 503s. The schema lacked indexes on
several foreign keys, CHECKs on `users.version`, the email statuses and
reasons and the time-ordering pairs, and mixed timestamp modes. jsonb
columns relied on callers to write objects (ISSUE-24). `debate_participants`
had no writer. `bun db:seed` wrote the `foundation` format, a second writer
beside the migration. `bun test:e2e` wrote into the test database whose row
counts integration evidence reads (ISSUE-17).

drizzle-kit 0.31.x (0.31.11 included) depends on
`@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils` →
`esbuild ~0.18.20`, which `bun audit` reports as GHSA-67mh-4wv8-2f99
(ISSUE-31). drizzle-kit 1.0 loads the config with `jiti` and depends on
`esbuild ^0.25.10`. The owner rejected `overrides`, `bun audit --ignore` and
exception registries as fixes.

## Decision

1. **Drizzle 1.0 release candidate, pinned exactly.** `drizzle-orm` and
   `drizzle-kit` are both `1.0.0-rc.4` (npm dist-tag `rc` on 2026-09-23;
   `latest` is still 0.45.3 / 0.31.11). Read before adopting, version
   matched: the drizzle-kit 1.0.0-rc.4 package's own skills
   (`node_modules/drizzle-kit/skills/drizzle-migrations`,
   `drizzle-generate`: `defineConfig`, the `generate` JSON envelope, the
   folder layout, Postgres roles and privileges surface) and the
   drizzle-orm 1.0.0-rc.4 sources `migrator.js` (folder reader),
   `pg-core/async/session.js` (migration table and single-transaction
   apply), `bun-sql/postgres/driver.js`, `session.js`, `codecs.js` and
   `pg-core/columns/custom.js`.
   - **Migration layout.** `packages/db/migrations/<YYYYMMDDHHMMSS>_<name>/`
     holds `migration.sql` and `snapshot.json` (snapshot format `8`, chained
     by `id`/`prevIds`); there is no `meta/_journal.json`, and the
     migrator refuses a folder that still has one. The migrator applies
     folders in name order and silently skips a folder without
     `migration.sql`.
   - **Relational query builder v2.** Daisy passes no `relations` to
     `drizzle()` and uses no `db.query`. Better Auth's drizzle adapter
     (1.7.5, peer `drizzle-orm ^0.45.2 || >=1.0.0-rc.1 <2.0.0`) reaches
     `db.query` only for its experimental joins, which are off, so it runs
     on the core query builder; the auth integration suites prove it.
   - **Driver change.** drizzle-orm 1.0's Bun SQL driver sets
     `client.options.bigint = true` on the client it is given: every
     `int8`/`bigserial` value that client returns is a `BigInt`, including
     raw queries on the same client. `createDatabase` owns its client, so
     only its own queries see this; `outbox.seq` was already a `bigint`.
   - **Names.** drizzle-kit 1.0 names default foreign keys `…_fkey` and
     primary keys `<table>_pkey`, while drizzle-orm's `getName()` still
     reports `…_fk`/`…_pk`. The database names are the truth; the schema
     test checks only explicitly named keys.
   - **Risk of a release candidate.** APIs and the snapshot format may
     still change before 1.0.0. Mitigations: exact pins, the generated
     SQL is reviewed and committed, `bun migrations:check` validates the
     layout and snapshot chain, and the integration suites exercise every
     adapter path against PostgreSQL 18. Moving to 1.0.0 is a normal
     dependency upgrade with `bun db:generate` expected to report no
     changes.
2. **One baseline, sanctioned once.** The five migrations are replaced by
   `20260923195259_baseline`, generated by drizzle-kit 1.0 and followed by
   a hand-written, reviewed tail (roles, grants, reference data) that
   drizzle-kit does not generate. `policy/migration-baselines.json` holds
   one sanction whose `baseMigrationsHash` is the sha256 of every committed
   path and blob under `packages/db/migrations` on the replaced base, so it
   works whatever layout the base had and is inert once the baseline lands.
   The ADR 0023 entry is removed.
3. **`bun migrations:check` reads the tree, not a journal.** It fails any
   file outside `<tag>/migration.sql` and `<tag>/snapshot.json` (a legacy
   `meta/` file included), a snapshot with no `migration.sql`, SQL with no
   snapshot, two folders sharing a timestamp, a broken `prevIds` chain, and
   any shared migration removed, displaced or edited (SQL or snapshot)
   relative to the merge base. Migration numbers no longer exist, so
   `bun adr:next` claims ADR numbers only.
4. **Runtime roles live in the baseline.** `daisy_web` (created if missing,
   LOGIN, no password) holds `SELECT, INSERT, UPDATE, DELETE` on every
   `public` table and `USAGE, SELECT` on every sequence, extended to later
   objects by default privileges, and nothing that alters schema: no
   `CREATE` on `public`, no `TRUNCATE`, `REFERENCES` or `TRIGGER`, no access
   to the `drizzle` schema. `daisy_realtime` keeps exactly ADR 0032's
   grants and receives no default privileges. Passwords are set out of
   band.
5. **Test logins are provisioned in one place.** `provisionTestRoles` in
   `packages/db/src/slots.ts` creates the loopback-only `daisy_e2e` login
   and makes it a member of `daisy_web`, with no grant of its own. `bun
slot:up`, `bun db:reset`, `bun slot:reset-e2e` and CI (`bun db:roles`)
   all call it after migrating. Membership is cluster-wide and the baseline
   re-grants `daisy_web`, so a reset loses nothing, and the browser suite's
   production server runs with exactly the runtime role's privileges. The
   template database is gone: slot databases are created from `template0`.
   Integration tests keep connecting as the migration owner, because their
   fixtures and role checks (`SET ROLE`) need it.
6. **Every jsonb column declares its shape (ISSUE-24).** `jsonbColumn(name,
schema)` cannot be declared without a zod schema; every write is parsed
   and a mismatch fails with an `AppError` `VALIDATION` before it reaches
   the driver. `jsonbIsObject` adds `<table>_<column>_is_object`
   (`jsonb_typeof(...) = 'object'`) to every jsonb column. Snapshots, format
   rules and outbox payloads use their `@daisy/protocol` schemas;
   `ballots.scores` and `debate_commands.result` have no writer or protocol
   contract yet and use `jsonObjectSchema` (any JSON object) until their
   first writer brings one.
7. **Integrity gaps closed.** Every foreign key has a full index that
   leads with its columns. CHECKs cover `users.version`, the email
   delivery status and its one rank (`(status, status_rank)` pairs),
   suppression reasons, `seasons.ends_at > starts_at`,
   `role_grants.revoked_at >= granted_at`,
   `ballots.voided_at >= submitted_at` and
   `debates.completed_at >= started_at`. `ballots` gains `created_at` and
   `updated_at`. Foreign-key columns are named for what they reference:
   `debates.format_id`, `debates.created_by_actor_id`,
   `ballots.judge_actor_id`. `DebateRecord` and `NewDebate` keep the domain
   names `format` and `createdBy`; `debate-record.ts` is the one mapping.
8. **One timestamp helper.** Every timestamp is `timestampColumn` or its
   recipes (timestamptz, Date mode); no schema file builds `timestamp()`
   itself. Time sources: row audit columns default to the database clock
   (`now()`, or `statement_timestamp()` where the outbox needs the write
   moment), and competitive times are PostgreSQL time (ADR 0033): the
   snapshot write path stamps `started_at`, `completed_at` and new seats'
   `joined_at` with the `statement_timestamp()` of the write (ISSUE-37).
9. **`debate_participants`' debater seats are the snapshot's
   projection.** Its key is `(debate_id, actor_id)` (snapshot participant
   ids are actor ids, ADR 0029). `createDebate` and `saveSnapshot` rewrite
   the `affirmative` and `negative` seats in the same transaction as the
   snapshot: role from side, slot by order within a side, status `joined`
   or `ready`, departed debater seats deleted, `joined_at` the database
   time of the write that first seated the actor. The snapshot does not
   carry judges, so a snapshot write never deletes or rewrites a judge seat
   (its `ballots` cascade from it) and refuses a snapshot that seats an
   actor already holding one (ISSUE-43). `ballots` and `rating_changes`
   reference that key.
10. **Reference data ships in migrations only.** The baseline inserts the
    `foundation` format; later reference rows arrive in forward migrations.
    `bun db:seed` writes only the dev fixture, through `@daisy/db/dev-seed`'s
    `applyDevSeed` adapter operation (ISSUE-8 AC4). `scripts/reference-formats.ts`
    mirrors the rows for tooling that runs without a database, and a test
    fails when the mirror and the migrations disagree.
11. **The browser suite has its own database (ISSUE-17).** Each slot has a
    third database, `daisy_e2e` in the main checkout and
    `daisy_wt_<id>_e2e` in a worktree, created and migrated by
    `bun slot:up`, emptied back to the baseline by `bun slot:reset-e2e`,
    and dropped by `bun slot:down` and orphan pruning. `E2E_DATABASE_URL`
    names it; `bun db:reset` does not touch it. CI's e2e job migrates its
    own `daisy_e2e` database as `daisy` and runs the server as `daisy_e2e`.

## Consequences

- Every local and test database, including every other slot, must be reset
  once after this merges, and the legacy `daisy_template` database dropped
  once (steps in the ISSUE-6 handoff). Staging must be reset too; that is a
  human-only sign-off leaf.
- Production and staging need `CREATEROLE` on the migration credential
  (unchanged since ADR 0032) and, to realise the runtime split, a
  `daisy_web` password and an app `DATABASE_URL` distinct from the
  migration credential. The release command still reads `DATABASE_URL`;
  separating the two is tracked as its own issue.
- `bun audit` no longer reports esbuild. The vitest and underscore
  advisories remain (ISSUE-31); ADR 0039 records them as dated, unreachable
  exceptions.
