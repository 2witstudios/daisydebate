# ADR 0006: Adobe Data behind a domain adapter

Status: accepted.

We need data-oriented domain execution without tying browsers, persistence, or future services to a particular ECS implementation. Use exactly `@adobe/data@0.10.19`, currently published under the stable registry tag, in `packages/debate-engine/src/ecs-adapter.ts` only. Its pre-1.0 status makes deliberate pinning mandatory.

Official sources: [repository and breaking changes](https://github.com/adobe/data), [API reference](https://adobe.github.io/data/), and version-matched package declarations under `node_modules/@adobe/data/dist/ecs`. These were inspected before implementation. Current plugin property ordering and synchronous transactions were checked against 0.10.19 declarations. Bun compatibility is verified by executing our contract tests, rather than assuming the upstream Node/browser support statement guarantees Bun.

Our API exposes UUIDs, operations, and JSON snapshots. Numeric ECS IDs, Adobe schemas, query interfaces, transaction internals, and vendor snapshots stay private. Snapshot restore hydrates a fresh database from our validated versioned representation; this trades some copying for portable persistence and stable upgrade semantics. ECS owns mutable component storage, not database rows or network transport.

Upgrade procedure: read release notes and the installed target declarations, update the exact version and lockfile, run engine contract tests plus typecheck and production build, and review changes for storage/lifecycle semantics. Add a failing regression test for every vendor behavior on which the adapter newly relies. Never persist a vendor-native snapshot without a separate migration decision. Removal requires replacing the adapter while keeping these contracts green.
