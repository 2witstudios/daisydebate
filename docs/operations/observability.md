# Observability

Provider-neutral OpenTelemetry instrumentation exists from day one; tracing
exporters belong to deployment, not the repository. Error tracking and
product analytics are the deliberate exception:
[ADR 0037](../decisions/0037-error-tracking-and-product-analytics.md) ships
the [PostHog product analytics adapters](product-analytics.md), inert without
deployment configuration and consent, alongside the Sentry error adapters. See
[compliance](compliance.md) for the consent rules
those adapters must follow. Any other vendor SDK still
requires its own ADR before it may be added.

The Sentry adapters are wired at `apps/web/src/features/telemetry/`
(`@sentry/nextjs`, server/edge/client configs and the reporter) and
`apps/realtime/src/telemetry/` (`@sentry/bun`). Each runtime initializes
only when its own variable is present (`SENTRY_DSN` for every server
capture path, `NEXT_PUBLIC_SENTRY_DSN` for the browser, read at runtime and
written per request on `<html>` by the root layout, so setting it needs no
rebuild and the CSP and the client read the same value), runs the pure
`scrubEvent` as `beforeSend` — which drops the request body, headers,
cookies, query string and IP, drops console breadcrumbs, reduces the user
to the cuid2 id alone, and replaces every raw exception message in the
error's whole linked-cause chain with a `[scrubbed]` marker, because a
database error's message carries its bound parameters: the type, stack
frames and mechanism pass through, and the bounded `errorCode` tag stays
the safe diagnostic channel — and collects nothing at the SDK level
(Sentry 11 `dataCollection`: no cookies, headers, query parameters,
bodies, user info, database payloads or stack-frame variables). An
unconfigured deployment's CSP names no vendor host, and the only
`@sentry/*` imports lint allows are inside those adapters plus
`apps/web/next.config.ts`, whose source-map upload runs only when a
deploy-time `SENTRY_AUTH_TOKEN` exists.

## Trace volume and privacy

DEC-368 sets an engineering policy shared by web server, edge, browser and
realtime: check-in (`/api/rounds/:id/check-in`, including `attendance.check-in`)
and health routes are not sampled; other roots have a local 1% probability.
This is not an absolute monthly quota: one million ordinary requests with
seven spans each estimates 70,000 spans. A single 1 Hz seven-span probe would
otherwise produce 18,144,000 spans per 30 days; even 10% would leave 1,814,400.
Suppression preserves its per-second public request and durable receipt.

An explicit `tracesSampler` overrides inherited `sampled=true`. Sentry11 also
accepts `sentry-sample_rand` baggage. The adapter's supported sampler callback
therefore makes an independent local CSPRNG Bernoulli decision and returns
0 or 1; upstream callers cannot force the 1% policy to become 100% by selecting
that draw. Sentry records a conditional sample probability of 1 for admitted
roots, so vendor extrapolated totals must not be interpreted as unbiased 1%
traffic estimates. Independent local admission deliberately breaks trace
continuity when downstream rejects a parent that was admitted upstream.
Automatic outbound propagation is restricted to the full trusted
`PUBLIC_APP_URL` origin on servers/realtime and current origin in the browser;
lookalike hosts, other ports and untrusted vendors receive no trace headers.
Routine check-in/health requests and `get-session` are excluded from propagation
even within that trusted origin. This matters in the browser SDK, whose scoped
`suppressTracing` stops span recording but still injects headers into an allowed
request. The path exclusion prevents those requests seeding downstream traces
while preserving ordinary trusted correlation.
The probe's check-in and independent hourly session-refresh fetch each run in
their own suppressed async scope. Other operations regain their context.

Sentry11.10.0 is explicitly pinned to its streaming lifecycle: `beforeSendTransaction` is ignored and
`beforeSendSpan` cannot drop a span. Root sampling and suppressed fetch scopes
prevent routine root capture; shared `ignoreSpans` filters also exclude routine
HTTP and named child spans under an ordinary sampled parent. Every delivered streamed span passes through the shared
pure `scrubSpan`, which removes query-bearing names/URL attributes, query and
SQL payload attributes, and scrubs linked attributes. Envelope dynamic-sampling
metadata drops its copied transaction name. Errors keep `sampleRate: 1` and
`scrubEvent` independently of trace sampling; missing DSNs remain inert. No new
data class, purpose, processor, retention or consent category is introduced.

Regression proof uses the actual installed SDK envelope transports and actual
outgoing HTTP headers with forced inherited sampling and controlled local
draws. The native Chromium SDK proof uses an isolated page and real HTTP targets;
it is SDK proof, not an application journey. Deployment verification must inspect actual
machine image SHA and runtime SDK options before interpreting delayed vendor
ingestion. A quiet vendor dashboard alone is never proof.

SDK references: [sampling](https://docs.sentry.io/platforms/javascript/guides/nextjs/sampling/)
and the installed11.10.0 `tracing/sampling.js`, `tracing/trace.js`,
`tracing/spans/beforeSendSpan.js` and `types/options.d.ts` are the checked
sampling, inheritance and streaming contracts.

## Source of truth

The structured event stream emitted by `@daisy/logger` is the operational
source of truth. Query the JSON log entries for what happened; use `traceId`
and metrics as supplementary correlation and aggregation. A trace may be
absent when the deployment has no OpenTelemetry provider, but lifecycle and
failure events still go to the logger destination. The logger event registry
is the source of truth for the permitted event names and their severities,
not a history of emitted events. See [ADR 0015](../decisions/0015-event-stream-as-observability-source-of-truth.md).

## Current state

- `@daisy/observability` wraps the OTel API only: `withSpan` for meaningful
  boundaries, `currentTraceId`, request-ID correlation, `withTimeout` for
  bounded waits. Without a provider installed, spans are no-ops — cheap and
  safe.
- `apps/web/src/instrumentation.ts` registers server runtime initialization
  and `onRequestError`, tagging unhandled failures with route, request ID,
  and deployment identity.
- `handleOperation` (web server layer) binds a request-scoped child logger with
  `operation`, `requestId`, and `traceId`, then emits
  `http.request.completed`, `http.request.cancelled`, or `http.request.failed`
  with structured lifecycle fields — never formatted strings.
- The Next Proxy validates an ingress `traceparent` before forwarding it; the
  HTTP boundary extracts that W3C context as the parent of the request span.
- The logger embeds `appVersion` and `gitCommit` (deployment identity) in
  every line; production config refuses to boot without them.
- Logger events use a compile-time vocabulary and registry-declared severity;
  callers emit through one event-based method, and untrusted runtime event
  names normalize to `telemetry.unknown_event`. Dynamic operation names remain
  structured context fields.
- Database and Redis adapters accept provider-neutral injected event sinks and
  emit `db.query.failed` or `redis.command.failed` with the operation name when
  an external query or command fails. They rethrow the original failure and do
  not depend on the logger package. Known workload-admission refusals mean
  work never ran: the DB boundary instead emits `db.capacity.refused` with
  the operation name, the lane and its pressure. Identity survives bounded native error cause
  wrappers; code/message lookalikes, unsupported cause links and execution
  timeouts remain failures. Auth suppresses duplicate unhandled-crash logs
  only for this identity. Failed HTTP requests still record their actual
  retryable 503; a deferred refusal preserves the response already sent.

## Retention and routing

On staging, the log shipper (`apps/log-shipper`) streams every app's stdout
from Fly's org log stream into a 6PN-only ClickHouse. The admin app's
Security page reads it through a read-only role
([ADR 0084](../decisions/0084-operational-log-pipeline.md),
[runbook](log-pipeline.md)).

- **Admission.** A line is stored only when `@daisy/logger/ingest`
  admits it against the registry and field table below. Anything else is
  counted by reason in `shipper_drops`, never stored raw.
- **Delivery.** The stream is at-most-once, and inserts are
  retry-idempotent, so counts are lower bounds. The page shows the
  shipper's heartbeat as coverage before any count.
- **Retention.** 28 days on receipt time ([compliance](compliance.md), "Operational logs").
- **Production.** Production uses its own Fly org and its own pipeline,
  rolled out by the owner.

The six round worker failure events (`round.maintenance.failed`,
`round.judging.failed`, `round.analysis.failed`, `round.control.failed`,
`round.speaking.failed`, `round.hearing.failed`) carry
the worker stage in `operation` and the error's own code (`INTERNAL` when
untyped). The raw error goes only to the scrubbed `ErrorReporter`. Two outcomes
are not failures: a lost lease (`CONFLICT` once the Round completes or the claim
rotates) releases silently, and shared-pool admission backpressure (ISSUE-431)
is a deferral that the next pass retries. A stage logs `<operation>.capacity`
on every ninth refusal, whatever its cadence, so a starved slow stage is still
reported. A bot speech refused admission keeps its delivery attempts and
resumes at the refused step: the provider answer and the phrases already spoken
are never bought or spoken again.

Lifecycle events describe runtime, server, and request progress. Failure events
describe invariant violations, unhandled requests, and adapter failures;
`http.request.cancelled` is an expected client-abort signal and is intentionally
warning-level rather than an error. Invariant events carry only the stable
`invariantId`; adapter events preserve the original failure for the caller to
handle and record only the safe operation context. Auth events carry only
`operation`, the stable auth route `path` where applicable, and an
`errorCode`: never the recipient, token, link URL, client address, limiter
key, or provider exception. The `auth.magic_link.*`, `auth.passkey.*`,
`auth.session.*`, and `auth.email_change.*` lifecycle milestones (AUTH-6.4)
carry only `operation` and their own name; they mark that a milestone
happened, not who it happened to — correlate the acting account through
`requestId`/`traceId` and the application's own audit trail, not the log
line. `auth.rate_limit.denied` is expected traffic and is warning-level;
alert on `auth.rate_limit.unavailable`, `auth.session.unavailable` and
`mail.failed`.

## How to answer production questions

Which request failed / what else happened to it: correlate `requestId`
(proxy-generated at the edge, echoed on responses and error bodies; the
operation layer also honors well-formed caller IDs when the proxy is bypassed)
with `traceId` once a provider is installed. Which deployment:
`appVersion`/`gitCommit` log fields. Which user: pass `userId` or
`actorId` as structured fields at feature-operation level — add them where
the operation knows them, not by re-parsing payloads. A log line carries
only the fields ADR 0019's loggable-field table admits.

For an incident, start with the event stream and filter by `event`, then
correlate `requestId`, `traceId`, `operation`, and deployment fields. The
registry alone cannot answer when an event occurred or which request emitted
it; those facts exist only in the emitted entries.

## Rules

- Instrument meaningful boundaries (HTTP operations, adapter calls,
  scheduled work), not every function.
- Never log credentials, cookies, raw request bodies, or raw exceptions.
  The logger admits only ADR 0019's allowlisted fields of their declared
  kind and fixed-prose messages; that is defense in depth, not permission.
- Tracing exporters/SDK: install at deployment edge (collector sidecar or
  platform integration). Adding an SDK to application packages requires an
  ADR; Sentry and PostHog are the standing exception under ADR 0037.
- Next.js instrumentation hooks are the supported framework surface; do not
  invent framework-specific telemetry.
